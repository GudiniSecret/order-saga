# Decisions

## 001. Монорепозиторий, сервисы — независимые Maven-проекты

**Дата:** 2026-10-25

**Решение:** один git-репозиторий; каждый сервис — самостоятельный Maven-проект
со своим `pom.xml` и Maven Wrapper, без общего parent-pom и shared-модулей.

**Альтернативы:**
1. Multi-module Maven с parent-pom и общим модулем для классов событий.
2. Отдельный репозиторий на каждый сервис.

**Почему:**
- Общий модуль с классами событий создаёт связанность на этапе компиляции:
  изменение события требует пересборки и одновременного деплоя всех сервисов,
  а это противоречит независимому деплою микросервисов.
- Отдельные репозитории для одного разработчика — лишние накладные расходы,
  и всё окружение сложнее поднять одной командой.

**Цена:** классы событий дублируются в каждом сервисе, контракт держим
в синхроне вручную.

## 002. Spring Boot 4.1 вместо 3.5

**Дата:** 2026-10-25

**Решение:** Spring Boot 4.1.x (Spring Framework 7, Hibernate 7, Jackson 3, Testcontainers 2).

**Альтернативы:** Spring Boot 3.5.x — больше материалов и примеров.

**Почему:** бесплатная поддержка 3.5 закончилась 30.06.2026, то есть до начала проекта:
новых патчей, в том числе по безопасности, не будет. 4.1 поддерживается до июля 2027.
Ключевые концепции (DI, транзакции, JPA, Kafka) не изменились.

**Цена:** часть туториалов написана под 3.x, их нужно адаптировать:
модульные стартеры, `@MockitoBean` вместо `@MockBean`, пакеты Jackson 3 `tools.jackson.*`.

## 003. Идентификаторы и деньги

**Дата:** 2026-10-26

**Решение:**
- UUID v4, генерирует приложение (Hibernate, `GenerationType.UUID`), для всего, что
  выходит за границы сервиса: `orders.id`, а также внешние `customer_id`, `product_id`.
- `BIGINT GENERATED ALWAYS AS IDENTITY` для внутренних сущностей: `order_items.id`.
- Деньги: `NUMERIC(12, 2)` в БД, `BigDecimal` в Java. Одна валюта, колонки `currency` нет.

**Альтернативы:** BIGINT везде; UUID с `DEFAULT gen_random_uuid()` в БД; UUID v7;
`NUMERIC(19, 4)`; типы `money` и `double precision`.

**Почему:**
- `orderId` — ключ Kafka-сообщения и поле событий, его не нужно согласовывать между
  сервисами, и по нему нельзя перебирать чужие заказы.
- UUID генерирует Hibernate, а не код вручную: при выставленном вручную id
  `save()` делает `merge()` с лишним SELECT перед INSERT.
- Позиции заказа не покидают сервис: BIGINT компактнее и монотонен.
- `double` накапливает ошибку округления; `money` зависит от локали сервера.

**Цена:** UUID v4 случайный, вставки разбросаны по B-tree индексу. При росте данных
переходить на UUID v7. Мультивалютность потребует миграции.

## 004. Цена позиции приходит от клиента

**Дата:** 2026-10-27

**Решение:** `price` передаётся в `POST /orders` и сохраняется как цена за единицу на момент заказа.

**Альтернативы:** брать цену из каталога (отдельный product-сервис или локальная таблица цен в `order-service`).

**Почему:** каталога нет в scope MVP; фокус проекта — сага и гарантии доставки.

**Цена:** клиент может подменить цену. В проде цену определяет сервер, клиент присылает только `productId` и `quantity`.

## 005. События сериализуются в JSON-строку, без type headers Spring Kafka

**Дата:** 2026-10-31

**Решение:** `StringSerializer` для ключа и значения; конверт события
(`eventId`, `eventType`, `orderId`, `occurredAt`, `version`, `payload`) сериализуется
в JSON через `JsonMapper` в коде сервиса. Тип события — поле `eventType`.

**Альтернативы:** `JacksonJsonSerializer` из Spring Kafka (с заголовком `__TypeId__`
или с отключёнными type headers и фиксированным целевым типом); Avro/Protobuf + Schema Registry.

**Почему:**
- Заголовок `__TypeId__` содержит имя Java-класса producer'а — связанность между
  сервисами на уровне классов, от которой мы отказались в 001.
- В одном топике несколько типов событий; диспетчеризация по `eventType` проще маппинга типов.
- В фазе 3 событие хранится в outbox как JSON-текст, relay отправляет его без преобразований.

**Цена:** нет проверки схемы на стороне брокера; совместимость контракта держим
полем `version` и тестами. Schema Registry — вне scope MVP.
